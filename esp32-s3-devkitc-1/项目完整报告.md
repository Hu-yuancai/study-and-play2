## 一、项目背景与意义

### 1.1 项目背景

随着电子设备和移动互联网的快速发展，学生群体在日常学习中普遍面临一个问题：**学习与娱乐之间的时间分配失衡**。适当娱乐能缓解学习压力、提高效率；但过度沉迷游戏又会严重影响专注度和时间管理。传统学习工具功能单一（仅计时或简单记录），缺乏互动趣味；而纯娱乐设备又容易导致长时间连续游玩，难以形成科学的学习习惯。

基于这一现实问题，我们设计了一种"**学习与娱乐相结合**"的嵌入式学习终端：既能提供适度娱乐放松，又能通过系统限制与学习机制，引导用户形成科学、高效、自律的学习方式——即本项目：**基于 ESP32-S3 的多功能学习游戏一体机**。

项目的核心思想不是单纯"做游戏"，而是通过"**学习 + 适度娱乐**"的模式提升学习效率与时间管理能力。系统结合学习模式与游戏模式，使用户在长时间学习后获得适度放松，同时通过**连续游戏时间限制机制**避免沉迷，达到劳逸结合、科学学习的目的。

### 1.2 系统总体介绍

系统以 TFT 彩屏作为主交互界面，OLED 副屏提供情绪反馈与提示，4×4 矩阵键盘实现模式切换与控制，无源蜂鸣器提供音效。整体分为**游戏模式**与**学习模式**两大部分：

- **游戏模式**：钢琴块、飞机大战、扫雷、贪吃蛇、俄罗斯方块、2048
- **学习模式**：番茄学习计时、背单词、数学速算、记忆翻牌

交互约定：4×4 键盘上 **A/B/C/D 对应上/下/左/右**（部分模块同时支持数字 2/4/6/8 方向）；**0 或 # 确认**；**\* 返回**。

### 1.3 为什么选择 ESP32 而非 51 单片机

本课程主要学习 51 单片机，但本项目最终选择 **ESP32-S3** 作为核心控制器。这一选择并非单纯追求"更高级"，而是基于**功能需求、系统复杂度与开发可行性**的综合考虑。

**(1) 运算能力差异。** 51 是经典 8 位单片机，主频通常仅 11.0592/12 MHz，RAM 与 Flash 很小，适合流水灯、数码管、简单按键等基础功能。而本项目需同时实现双屏显示、多游戏逻辑、图形刷新、定时控制、多任务交互。最直观的硬约束是**显存**：主屏 240×320 像素、每像素 16 位（RGB565）的帧缓冲需约 **150 KB**——而经典 51 的 RAM 仅 256 字节加少量扩展，**连零头都放不下**。ESP32-S3 为 32 位双核、主频可达 240 MHz、512 KB SRAM，足以承载图形界面与复杂游戏逻辑。

| 指标 | 经典 51 | ESP32-S3 | 本项目需求 |
| --- | --- | --- | --- |
| RAM | ~256 B + 少量扩展 | 512 KB SRAM | ≥150 KB（帧缓冲） |
| 主频 | 11~12 MHz | 240 MHz 双核 | ~60 FPS 实时刷新 |
| Flash | 8 KB 级 | 8/16 MB | 多游戏 + 字库 + 表情 |
| 运算 | 8 位 | 32 位 | 坐标运算、判定 |

**(2) 显示驱动能力差异。** TFT 通过 SPI 高速刷新图像，OLED 通过 I²C 实时显示。51 同时驱动多显示设备时易出现刷新慢、图像闪烁、程序阻塞；ESP32 具备更高的 SPI/I²C 速度，可支持双屏协同显示。

**(3) 关键：接口原理一脉相承。** 尽管换了芯片，本项目用到的接口技术都是课内讲过的同一套原理：矩阵键盘行列扫描（51 用 P1/P2 口、ESP32 用 GPIO，算法一样）、PWM 蜂鸣器（都是"方波频率决定音调"）、SPI/I²C 同步串行总线、UART 串口通信。**芯片是会过时的工具，接口原理才是不变的内核**——本项目是把课程学到的接口原理迁移到资源更强的平台上，去实现 51 受限于资源做不到的综合应用。

### 1.4 项目意义

本项目最核心的意义不在于"做了几个小游戏"，而在于尝试解决学生群体"学习与娱乐缺少平衡"的真实痛点，让娱乐真正服务于学习：

1. **学习引导设计**：与普通游戏机不同，系统加入"学习引导"思想——游戏连续运行不超过 10 分钟，超时即提示并引导进入学习模式。目的不是限制娱乐，而是帮助用户建立科学的学习节奏。
2. **寓教于乐的学习模式**：2048 训练数学逻辑与对 2 的幂的敏感度；背单词帮助英语词汇记忆；数学速算训练心算；记忆翻牌锻炼记忆力；番茄计时培养专注与时间规划。
3. **情感化的用户体验**：双屏交互 + OLED 动态表情反馈 + 蜂鸣器音效，让设备具备情感化交互能力，提高主动学习意愿。
4. **工程实践价值**：综合运用矩阵键盘扫描、SPI/I²C 通信、图形界面绘制、状态机控制、PWM 音频输出、多模块协同设计，是对"微机接口原理"课程知识的综合实践。

## 二、代码实现与仿真绘制（基础模型）

本章围绕**基础模型**展开：先确立硬件架构与引脚，再实现基础游戏与软件框架，最后用功能仿真验证。这是整个项目的地基。

### 2.1 系统硬件架构

```
                    ┌─────────────────────────┐
                    │      ESP32-S3 主控        │
                    │   (240MHz 双核, 512KB RAM) │
                    └─────────────────────────┘
       SPI │            I²C │          GPIO │         PWM │
           ▼                ▼              ▼             ▼
   ┌──────────────┐  ┌────────────┐  ┌──────────┐  ┌──────────┐
   │ ILI9341 彩屏  │  │ SSD1306    │  │ 4×4 矩阵 │  │ 无源蜂鸣器│
   │ 240×320 主屏  │  │ OLED 副屏   │  │  键盘     │  │          │
   └──────────────┘  └────────────┘  └──────────┘  └──────────┘
```

各模块职责：TFT 屏负责游戏画面与主界面；OLED 屏负责表情、提示与辅助状态；矩阵键盘负责模式切换与控制；无源蜂鸣器负责音效。各接口对应的课程知识：

- **4×4 矩阵键盘（行列扫描）**：4 行输出、4 列输入上拉，逐行拉低读列，配合软件消抖。
- **ILI9341 彩屏（SPI）**：SCK 时钟 + MOSI 数据 + CS/DC/RST 控制，内存帧缓冲整帧推送。
- **SSD1306 OLED（I²C）**：SDA+SCL 两线，7 位地址 0x3C 寻址。
- **无源蜂鸣器（PWM）**：方波频率决定音调，LEDC 硬件 PWM 输出。

引脚分配表见第三章（与原理图一并给出）。

### 2.2 软件框架与基础游戏

代码用 C/C++ 编写（与 51 的 C 编程思维相通），按"底层接口驱动 + 上层应用"分层，主程序用 `currentMode` 状态机调度各模块。基础模型阶段实现了**七个基础游戏**与番茄计时：

| 模块 | 简介 | 锻炼/特点 |
|---|---|---|
| 钢琴块 | 4 轨音符下落，到判定线按对应键，命中发声 | 节奏感；含长按、连击、判定等级 |
| 飞机大战 | 控制飞机移动射击，躲避并击落敌机 | 反应；动态难度提升 |
| 扫雷 | 数字提示推断雷区 | 逻辑推理、空间判断 |
| 贪吃蛇 | 吃食物增长，避免撞墙撞身 | 反应、路径规划 |
| 俄罗斯方块 | 方块移动旋转、消行 | 空间想象 |
| 2048 | 滑动合并相同数字 | 数学思维、对 2 的幂敏感 |
| 番茄计时 | 设定时长专注倒计时 | 专注与时间规划 |

下面以**钢琴块**为例，详述其代码实现与仿真调试的完整过程（最具代表性，对应《钢琴游戏模块开发与仿真技术报告》）。


### 2.3 钢琴模块的设计与代码实现

钢琴块是系统的核心娱乐子系统，设计目标：① 游戏逻辑——音符下落、矩阵键盘按键判定、得分统计、失败复位；② 音频驱动——PWM 波形驱动蜂鸣器实现多音高实时演奏；③ 双屏联动——主屏显示音符下落，副屏显示表情。

关键算法思路（均由接口原理引出）：矩阵键盘用行列扫描法读取按键；音符按时间轴下落，到达判定线时按"时间偏差"判定 Perfect/Good/Miss；命中时用 LEDC PWM 输出对应频率方波发声（频率决定音高）。

### 2.4 开发环境与编译工具链问题

**(1) Arduino IDE 中文路径乱码（status 1 & 2）。** Windows 下首次安装 Arduino IDE，编译报 status 1。原因是用户目录含中文（如 `C:\Users\张三\...`），编译链底层工具解析含中文路径时编码乱码。尝试改装到 D 盘全英文路径、用免安装 ZIP 版均无效（核心组件/缓存仍写入中文用户目录）。最终通过手动修改 `arduino-cli.yaml` 指定全英文编译缓存路径解决；其间还遇到 status 2，查到是某教程在添加 `build_cache` 配置项时漏了一个下划线，补全后打通编译链。

> 这一中文路径问题在后续 PlatformIO 阶段**再次出现**（链接器无法写 .map 文件，见第四章），是 Windows 嵌入式工具链的普遍坑。

### 2.5 双平台仿真之一：Wokwi 功能仿真

> **平台简介：Wokwi** 是一个支持 ESP32、Arduino 等的在线电子仿真平台，能直接搭建虚拟电路并运行真实固件、显示屏幕画面与交互，弥补了 Proteus 不支持 ESP32 的不足。

由于 **Proteus 元件库中没有 ESP32-S3 模型**，无法直接仿真 ESP32 程序，故功能仿真采用 Wokwi。过程中遇到的问题：

**(1) 仿真器件替代。** Wokwi 原生库缺乏原定的 LCD12864，对比替代型号后改用 TFT 显示屏，并同步改写了底层显示驱动代码。

**(2) 本地化编译重构。** Wokwi 网页端启动仿真显示超时。查阅资料后改用更高效的方案：

> **平台简介：PlatformIO** 是 VS Code 上的专业嵌入式开发插件，集成编译、库管理、烧录与调试，配合 Wokwi 插件可实现"本地编译 + 本地仿真"。

配置 C++/Python 插件、安装 PlatformIO 后导入项目，它会自动下载 ESP32-S3 的编译器/工具链/库（存放在国外服务器，需科学上网）。但多次导入、等待数小时仍失败，国内镜像源也无改善。查阅发现可能是 **Anaconda 的 Python 与 PlatformIO 冲突**——解决办法是从 Python 官网装一个独立干净的 Python，在 VS Code 中指定 PlatformIO 使用它（而非 Anaconda 的 Python），最终成功导入。随后按官方教程在项目根目录创建 `wokwi.toml`，告诉 Wokwi 去哪里找 PlatformIO 本地编译生成的固件，实现"一键编译 + 一键仿真"。

**(3) 运行期卡死与引脚冲突。** 联动仿真启动后，系统精确运行到 **0.808 秒** 时整个虚拟主控板卡死。经代码断点与引脚电平排查，确认是**引脚复用冲突**（ESP32-S3 部分 GPIO 有特殊用途，如 Flash/PSRAM 通信、Strapping 引脚，不能随意占用）。重新查阅技术规格书规避敏感引脚后，仿真恢复正常——这也是最终引脚分配表的由来。

**(4) 中文显示乱码。** TFT 仿真屏上中文乱码，原因是 Wokwi 标准 TFT 模型与基础驱动库不含中文字库。完整中文需自制汉字字模（逐字转点阵），较繁琐；为加快进度，主屏界面暂统一用英文，中文信息改由带 GB2312 字库的 OLED 副屏承担（这也是后续背单词模块"主屏英文、副屏中文"设计的由来）。

### 2.6 性能优化：非阻塞状态机

- 优化前：原始代码在音符刷新、按键消抖、蜂鸣器发声时大量使用 `delay()` 阻塞函数，CPU 延时期间原地死等，音符下落严重延迟。
- 优化后：把 `delay()` 全部替换为基于 `millis()` 的非阻塞计时——不停下程序，而是记录时间、到点再执行，使音符下落、按键检测、音频播放等多任务并行。
- 补充：仿真时仍感到一定延迟，经求证这是 Wokwi 软件本身的性能限制，同样代码烧录到真实 ESP32 上运行非常流畅。

### 2.7 音准校准

为确保演奏听感真实，专门另开测试项目，单独校准 ESP32 在各种 PWM 占空比和频率下的实际听觉音高，修正代码中的音符频率表，使不同轨道对应准确的音阶。

## 三、原理图的绘制

功能仿真验证了"方案能否实现、代码能否运行"，但要把系统做成实物，还需要一张能指导接线的**电路原理图**。这正是双平台仿真的另一半。

### 3.1 为什么仿真图之外还要画原理图

Wokwi 只关注"功能实现"，通常只显示 ESP32、屏幕、键盘、蜂鸣器等主要功能模块，而对**电阻、电源网络、上拉电阻、接地关系**等底层电路细节不完整体现——但这些在实物搭建中是必须的（OLED 的 I²C 需上拉电阻、所有模块必须共地、需明确 3.3V 与 GND 连接、GPIO 必须与真实引脚对应）。因此：

> **Wokwi 仿真图验证"方案能否实现"，Proteus 原理图指导"实物如何接线"**，二者各司其职、缺一不可。

我们选 Proteus 画原理图，因为它偏向电子工程的电路设计与原理图表达，能清晰展示模块间连接，适合后续实物搭建参考。

### 3.2 替代元件法

绘图中遇到一个问题：**Proteus 自带元件与实际购买器件不完全对应**——OLED 只有 SSD1306 裸芯片没有现成模块、TFT 型号不完全一致、蜂鸣器与键盘的引脚排列与实物有差异。若直接用自带元件，原理图引脚定义可能与真实硬件不一致，导致接线错误。

我们没有执着于寻找"完全一致"的模型，而是回到原理图的本质目的——**指导接线**。于是采用工程化方法：

> **用"具有相同引脚数量的连接器元件"代替真实模块，再按真实器件的引脚顺序重新定义每个引脚功能，并将连接器引脚与真实器件引脚一一对应。**

这样虽不是"真实模块模型"，但保证了引脚顺序真实、GPIO 对应真实、接线关系真实、实物可用。

### 3.3 连接关系与电阻设计

系统划分为 ESP32 主控、TFT 主屏、OLED 副屏、4×4 键盘、无源蜂鸣器。OLED 用 I²C（SDA/SCL 两线）；TFT 用 SPI（MOSI/MISO/SCK/CS/DC/RST 多线）；键盘用行列扫描（4 行 4 列）。

原理图特别加入两个 **4.7kΩ 上拉电阻**：I²C 的 SDA/SCL 是开漏输出，必须靠上拉电阻拉高才能稳定通信，缺少上拉会导致 OLED 无法显示、通信失败。此外明确了 **3.3V 电源网络与 GND 共地网络**——所有模块必须共地，否则会出现显示异常、按键失灵、通信错误。

## 四、实物制作（搭建与调试）

依据第三章的原理图与引脚表，用面包板免焊搭建实物，按"接线 → 通电 → 逐个点亮外设 → 联调"推进。过程中遇到 6 个典型问题，每个的排查都用到了接口原理与电路常识。本章是项目的核心实操环节。

### 4.1 编译工具链：中文路径导致链接失败

转用 PlatformIO 后第一次编译，所有源文件都编译通过，但**链接阶段失败**，报 `cannot open map file ... No such file or directory`。观察路径发现工程目录含中文，而 ESP32 的 GNU 链接器 `ld.exe` 在 Windows 下处理非 ASCII 路径有缺陷，无法创建 `.map` 文件。解决：`.map` 仅用于内存分析、对固件无影响，于是写一个构建脚本 `disable_map.py` 在链接前移除 `-Wl,-Map=...` 选项；关键是脚本必须用 `post:` 时机加载（该选项由框架在构建时添加，`pre:` 太早无效）。

> 这与第 2.4 节 Arduino 阶段的中文路径问题前后呼应，是同一类工具链坑在不同环节的体现。

### 4.2 接线完成，仿真能跑但屏幕不亮

按引脚表接好线，ESP32 上电（板载蓝灯亮）、烧录成功、仿真正常——但实物彩色主屏不亮。判断逻辑：仿真已验证程序正确 ⇒ 问题在硬件侧。

【图 5：第一次接线完成（预留——记录"接线完成，仿真可以跑但是屏幕不亮"）】

### 4.3 两个接线/供电问题

**问题 1：USB 接口插错口。** ESP32-S3 有两个 USB-C 口——一个是芯片**原生 USB（USB-Serial-JTAG）**，一个是板载 **CH343 桥接芯片的 UART/COM 口**。最初插原生 USB 口导致行为异常，改插 COM 口后恢复（从 VID/PID 可区分：原生 303A:1001，CH343 1A86:55D3）。

**问题 2：两块面包板的电源轨没联通。** 两块板的正负母线之间没用跳线连起来，接在第二块板上的副屏取不到电；把两块板的 +/− 轨分别联通后副屏点亮。

【图 6：发现接口与电源问题、副屏点亮（预留——记录"问题1：接口有误…问题2：两块面包板电源没联通"）】

> 用到串行链路识别（两个 USB 口对应不同链路）与供电回路常识（模块要工作 VCC/GND 必须接入同一网络；面包板电源轨中间常断开，跨板必须显式联通）。

### 4.4 大屏仍不亮：接口错位（逐线复查法）

副屏亮了但彩色大屏仍不亮。采取系统化排查：**另取一块同型号屏，对照引脚丝印，逐根线重新接、逐根核对。** 最终发现根因是**接口错位**——之前是"按引脚物理位置从上往下数"来接的，而 ILI9341 不同批次丝印顺序不完全一致，"数位置"导致整排错位，SPI 的 CS/DC/SCK 没接对。

【图 7：排查大屏不亮、逐线重接（预留——记录"大屏不亮，逐一接线，最后发现是接口错位"）】

经验教训：**两块板并排照着接很容易接错，一定要先拍摄/记录模块背面引脚分布图，按丝印名称接线，而非数物理位置。**

【图 8：屏幕引脚丝印特写（预留——记录"要提前拍背面引脚分布图"）】

> 对应 SPI 时序与信号定义：只有 CS/DC/SCK/MOSI 逐一对应正确，SPI 通信才能建立；任一错位即黑屏。逐线复查本质是"按信号定义核对接口连接"。

### 4.5 确认键盘映射（串口监视调试法）

大屏点亮后联调。曾怀疑键盘映射不对，用**串口监视调试法**：烧入键盘自检程序，每次按键通过 UART 打印"行号、列号、键值"，逐个按 16 键对照。结果证实键盘行列扫描与映射完全正常，从而排除键盘嫌疑、定位到上层逻辑。

> UART 串行通信的典型应用：用串口把单片机内部状态"打印"出来，是嵌入式调试最基本有效的手段。

### 4.6 白屏闪动 + 蜂鸣器间断：供电欠压（BROWNOUT）

功能跑通后出现更隐蔽的问题：屏幕偶发白屏闪动、蜂鸣器间断响、操作时画面"跳回"。用串口观察复位原因，捕获到 `rst:0xf (BROWNOUT_RST)`——**欠压复位**：芯片内置掉电检测发现电压跌破阈值自动复位保护，每次复位都重新初始化 LCD（白屏闪）、重播上电流程（蜂鸣器间断）、回到菜单（画面跳回）。

根因：所有外设（尤其 ILI9341 背光 LED 耗电大）都从板载 3.3V 取电，电脑 USB 供电有限；当"刷屏 + 蜂鸣器发声"同时发生（如得分时），瞬时电流尖峰把电压拉垮。解决（软硬结合）：① 软件减负——去掉上电开机音、降低待机 OLED 刷新频率；② 硬件供电——改用手机充电头（5V/1A 以上）供电。改进后复位原因变回正常的 `rst:0x1 (POWERON)`。

> 综合"供电能力"与"复位机制"：系统不仅逻辑要对，还要保证供电扛得住峰值电流——这是从仿真到实物才会暴露的真实工程问题。

### 4.7 调试过程汇总

| # | 现象 | 排查方法 | 根因 | 解决 | 知识点 |
|---|---|---|---|---|---|
| 1 | 编译过但链接失败 | 看报错路径 | 中文路径致 ld 无法写 .map | 构建脚本移除 -Map | 工具链/链接 |
| 2 | 屏幕不亮 | 先排除软件 | 见 3、4 | —— | 故障定位 |
| 3 | 供电/烧录异常 | 区分两 USB 口、查电源轨 | 插错口 + 跨板电源未联通 | 改插 COM、联通电源轨 | 串行链路、供电回路 |
| 4 | 大屏黑屏 | 逐线复查、对照丝印 | SPI 引脚错位 | 按丝印重接 | SPI 信号定义 |
| 5 | 按键疑似不对 | 串口打印行列键值 | 实为正常 | 定位上层逻辑 | UART 调试 |
| 6 | 白屏闪+蜂鸣器乱响 | 串口看复位原因 | BROWNOUT 欠压 | 减负+换强电源 | 供电、复位机制 |

> 工程调试方法论：先用仿真锁定软件正确性，再用串口/逐线法把问题逐步收敛到具体硬件环节，每步都有依据。至此基础模型在实物上跑通。

### 5.3 背单词模块

- **翻卡片**：主屏显英文 → 按确认看释义 → 自评"记得/不记得" → 下一个。
- **选择题**：主屏英文 + 副屏 4 个中文释义选项，按 1-4 选，报对错计分。

> 设计巧思：主屏（Adafruit GFX）只支持英文，中文释义放在带 GB2312 字库的 OLED 副屏——**主屏英文、副屏中文**，双屏各司其职。这一思路正源于第 2.5 节遇到的中文字库问题。

### 5.4 数学速算模块

每轮 10 题，主屏显示算式 + 4 个数字选项，按 1-4 选答，结算显示得分/用时/评级。做成选择题是因为键盘物理 0/9 是确认/射击键，无法干净输入任意数字。**难度随题号递增**：数值规模分三档（加法最大到 500、乘法到 25×25），进阶档出现三数连算（如 45+30-12），干扰选项幅度随答案大小自适应。

### 5.5 记忆翻牌模块

4×4=16 张牌=8 对字母，翻开两张找配对：相同则保留，不同则盖回，统计步数，全配对显示胜利。锻炼记忆力。支持方向键 A/B/C/D 与 2/8/4/6。

### 5.6 游戏限时机制（学习引导核心）

系统在主循环中统一计时：处于 6 个游戏模式之一时累计游玩时间，**连续超 10 分钟**即弹出"Time's up! Take a break, study!"并强制回主菜单；学习模式不计时。该机制实现于 `main.cpp` 主循环，**不侵入各游戏代码**，是"学习引导"理念的核心落地。

### 5.8 动态表情包的技术实现（亮点）

让 **128×64 单色** OLED 显示生动甚至会动的表情，是一个有意思的技术点。

**(1) 单色屏显示位图原理。** OLED 每像素只有"亮/灭"，要显示图必须先转成**单色点阵位图**：每像素 1 bit，128×64 = 1024 字节，驱动按 bit 数组逐点点亮。

**(2) 手工方法（字模软件）。** 最初做法：画图软件裁剪成 128×64 → 导出 BMP 单色位图 → 用 PCtoLCD 软件把每像素转成十六进制、生成 C 数组 → 复制进代码。对单张可行，但 18 张还要做动画则效率低。

**(3) 本项目的自动化方法。** 编写 Python 脚本（`tools_emoji_convert.py`，基于 Pillow）批量处理 18 张彩色表情图：解码降采样（避免 2048×2048 大图内存问题）→ 等比缩放居中裁剪到 128×64 → 阈值二值化 → 打包成 U8g2 的 XBM 格式字节数组（每字节 8 像素、LSB 在左）→ 生成 `emoji_bitmaps.h`（18 个 PROGMEM 数组 + 分组动画表）。相比手工 PCtoLCD，一次处理全部、且直接按分组生成动画表，是对原始字模流程的工程化升级。

**(4) "动态"的实现：多分镜循环。** 把同一动作拆成 2~3 个（或更多）分镜，按固定间隔循环切换形成帧动画。18 张按动作编成 **5 组**（如 1-3 一组、7-11+18 一组等）。OLED 驱动新增 `oledPlayEmojiAnim`/`oledPlayEmojiIdle` 函数，在**主菜单待机**和**番茄钟专注期间**调用：每帧约 600ms、每组约 4.5 秒切换，且仅在帧变化时刷新以降低 I²C 负载与平均电流（呼应欠压调试的经验）。

> 技术点串联：I²C 显示接口 + PROGMEM 程序存储器（大体积位图放 Flash 而非 RAM）+ "控制刷新频率降低平均电流"的供电经验。

### 5.9 隐藏彩蛋：Ghost Shell 调试终端

在开发后期，我们为系统加入了一个隐藏彩蛋——**Ghost Shell**：一个伪装成"电影黑客界面"的隐藏调试终端，既是趣味彩蛋，也是一个实用的参数调试工具。

**(1) 触发方式（隐藏入口）。** 在主菜单输入经典的 Konami 秘籍码，屏幕上没有任何提示：

```
↑ ↑ ↓ ↓ ← → ← →  +  9  +  0
（对应物理键：A A B B C D C D 9 0）
```

连续按对 10 个键后，蜂鸣器"嘀嘀嘀"三声，切入黑底绿字的 Ghost Shell 界面。这种"秘籍码触发、菜单无入口"的设计，正是彩蛋的乐趣所在。

**(2) 功能。** Ghost Shell 是一个**十六进制内存编辑器 + 参数速改菜单**：
- **内存编辑器**：以经典 hex dump 形式显示一块内存区，方向键移动光标，可查看/修改字节、跳转地址、切换 HEX/DEC/BIN 显示。
- **Hack 菜单**：按参数名快速调整游戏参数，例如扫雷的棋盘宽高、雷数、作弊透视开关等，调整后立即生效——演示时可借此快速把扫雷改成超简单局或开启全图透视。

**(3) 安全设计（关键）。** 它操作的对象**不是真实内存**，而是一块专门的 **64 字节沙盒内存 `safeRAM`**。所有写操作都经过带边界检查的接口 `safeRAMPoke`：越界地址、只读地址、超范围的值一律被拒绝并报警，**碰不到真实内存、不会让系统崩溃**。这是一个"安全沙盒后门"——既有黑客界面的趣味与演示价值，又不会带来任何系统风险。

> 这个彩蛋串联了多个知识点：Konami 码用一个**按键序列状态机**识别（每按对一个键状态前进，按错则回退）；hex 编辑器体现了对**内存/地址/进制**的理解；沙盒内存 `safeRAM` 则是一种**安全边界设计**思想。它虽是彩蛋，却也是一次有意思的工程小练习。

### 6.2 课程知识的综合运用

本项目虽以 ESP32-S3 为载体，但其内核——微机接口原理——与课程完全贯通：

- **接口类型全覆盖**：矩阵键盘（GPIO 行列扫描）、SPI、I²C、PWM、UART，课程讲的接口几乎都亲手接线、亲手调通。
- **方法论的运用**：原理分析 → 代码实现 → 功能仿真（Wokwi）→ 原理图设计（Proteus）→ 实物制作与联调，是一条完整的工程链路。
- **真实问题的解决**：中文路径链接失败、USB 口识别、SPI 接口错位、供电欠压、引脚复用冲突——都是只有动手做实物才会遇到、且必须用接口与电路知识才能解决的问题。

### 6.3 关于平台选择的再认识

选 ESP32 而非 51，不是"逃避"，而是因为应用的资源需求（150KB 彩色帧缓冲、实时性、双屏）客观上超出了 8 位单片机的物理能力。但这反过来印证了课程价值：**接口原理是平台无关的**——行列扫描、PWM、串行总线的知识原封不动迁移到了更强的平台上。

### 6.4 项目特色与开发模式

- **学习引导理念**：游戏限时 + 寓教于乐的学习模块 + 双屏动态表情，让设备真正服务于学习。
- **"基础先行、增量扩展"的开发模式**：先把核心硬件与基础游戏做成稳定的"基础模型"，跑通后再纯软件叠加新模块——这使系统易于扩展、调试范围可控，也是良好的工程实践。

### 6.5 实物调试的最大收获

仿真与实物之间隔着一道"工程鸿沟"：仿真里电源理想、引脚自动对齐；实物里引脚要按丝印一根根接对、电源要扛得住峰值电流、USB 要插对端口。**把仿真做对只是第一步，把实物调通才是真正的工程**，靠的是"先锁定软件、再逐项排查硬件、每步用原理找依据"的系统方法。

### 6.6 后续可改进方向

- 给彩屏背光加限流/独立供电，从硬件上根治欠压；
- 把矩阵薄膜键盘换成手感更好的按键键盘；
- 为主屏制作中文字模，使界面支持中文；
- 增加更多接口类型（如 ADC 摇杆、I²C 传感器）。
