一、这个工程是怎么做出来的（诚实说明）

为了让汇报站得住脚，先把"人做了什么、AI 做了什么"讲清楚。我们的态度是：工具用得坦荡，但工程判断在人。

真实的开发时间线

  1. 起步——人。 最初用 Arduino IDE 手写代码，从点亮一块屏、扫描键盘做起，搭出最初的框架。
  2. 钢琴音调——人的用心。 钢琴模块的音高设计是重点，它延续了我们之前用 C51 播放音乐的思路（用方波频率对应音阶）；还专门另开测试工程，逐个校准 ESP32 在不同 PWM 频率下的真实听感音高。
  3. 引脚排布——人。 引脚分配是我们查 ESP32-S3 规格书、避开复用/敏感引脚后定下来的（仿真时还踩过引脚冲突的坑），并画了 Proteus 原理图和引脚对应表指导接线。
  4. 实物搭建与调试——人。 面包板接线、屏不亮/接口错位/供电欠压等一系列问题的排查，全是动手做出来的（详见最后"调试历程"）。
  5. 实物跑通后——AI 加速。 平台稳定后，后续新增的多个模块（扫雷、贪吃蛇、俄罗斯方块、2048、背单词、数学速算、记忆翻牌、动态表情包等）我们较多地借助 AI 直接生成代码，大幅提速。
人类不可替代的作用 即便后期用 AI 写代码，"做什么、怎么算对、哪里不对"始终是人在判断：
  • 反映真实需求：提出"学习机要防沉迷"→ 设计游戏限时机制；发现键盘只有数字键 → 把数学/背单词改成选择题；觉得 ABCD 当方向反直觉 → 加 2/4/6/8 方向键。
  • 实机调试与 debug：钢琴判定线和得分时机对不上、飞机射击按了没反应、得分时白屏重启……这些都是真机上跑出来、再定位修复的。
  • 工程取舍：为什么用 ESP32 不用 51、为什么主屏英文副屏中文、表情包刷新频率怎么定，都是结合硬件约束做的判断。
一句话汇报口径“硬件方案、引脚设计、核心音频思路和全部实物调试是我们做的；功能模块的代码实现部分借助了 AI，但每个模块的需求定义、参数调整和真机验证都由我们完成——AI 是加速器，工程判断在我们手里。”
人主导设计/调试/判断 人机协作人定需求+AI实现+人验证 AI 为主实物稳定后的增量模块

二、总体架构：分层设计

整个工程遵循一个清晰的分层思想：把"怎么和硬件打交道"封装成驱动，上层游戏只管调用。这正是接口编程的核心。

┌─────────────────────────────────────────────┐
│  应用层：10个功能模块 + 1个隐藏彩蛋             │
│  钢琴 飞机 扫雷 蛇 俄罗斯 2048 / 番茄 背单词 数学 记忆 / Shell │
├─────────────────────────────────────────────┤
│  调度层：main.cpp 主程序                       │
│  状态机(currentMode) + 菜单 + 游戏限时          │
├─────────────────────────────────────────────┤
│  驱动层：把硬件封装成函数                       │
│  keyboard(键盘) lcd_driver(主屏) oled_driver(副屏) audio(音频) │
├─────────────────────────────────────────────┤
│  配置层：config.h 引脚与键值定义                │
├─────────────────────────────────────────────┤
│  硬件：ESP32-S3 + TFT + OLED + 4×4键盘 + 蜂鸣器 │
└─────────────────────────────────────────────┘
为什么这样分好处是解耦：写一个新游戏（比如贪吃蛇）时，根本不用关心"屏幕怎么用 SPI 刷新""按键怎么扫描"，直接调 lcdFillRect()、scanKeyboard() 就行。这也是为什么实物跑通后能快速叠加新模块——驱动层是稳定的地基。

三、主程序流程（main.cpp）

理解了 main.cpp，就理解了整个系统怎么转。它就是一个标准的"初始化 → 无限循环"的单片机程序。

setup()：开机初始化（只跑一次）

Serial.begin(115200);   // 串口，用于调试日志
safeRAMInit();          // 初始化彩蛋用的沙盒内存
initAudio();            // 配置 PWM 音频
initKeyboard();         // 配置键盘 GPIO（行输出、列上拉）
initLCD();              // 初始化彩屏 SPI
initOLED();             // 初始化 OLED I2C
drawMenu();             // 画出主菜单
这里藏着一个调试故事原本这里有一句开机提示音 playTone(880,100)，后来发现它在上电最脆弱的瞬间叠加电流，会触发欠压重启，被我们删掉了。这就是"真机调试反推代码"的例子。

loop()：主循环（每 16ms 一圈，约 60 帧/秒）

uint8_t key = scanKeyboard();   // 1. 扫描键盘，拿到当前按键
audioUpdate();                  // 2. 推进非阻塞音效

// 3. 游戏限时检查（防沉迷）：玩游戏累计超10分钟→踢回菜单
if (isGameMode(currentMode)) { ...超时则回菜单... }

// 4. 按当前模式，把按键交给对应模块处理
switch (currentMode) {
  case MODE_MENU:   handleMenu(key);    break;
  case MODE_PIANO:  pianoGameLoop(key); break;
  case MODE_SNAKE:  snakeGameLoop(key); break;
  ... // 共10个功能 + Ghost Shell
}
delay(16);
核心思想：状态机用一个变量 currentMode 记住"现在在哪个功能"，主循环根据它把按键分发给对应模块。切换功能 = 改这个变量。这是单片机里管理多界面/多模式最经典的写法，也是课程里"程序状态机"的标准应用。

这是人做的功夫引脚不是随便排的。ESP32-S3 有些 GPIO 有特殊用途（接 Flash/PSRAM、上电时是 Strapping 引脚），占用会导致启动异常——我们仿真时就在 0.808 秒卡死过，正是引脚复用冲突。最终这张表是查规格书、避开敏感引脚定下来的（注意行用了 1/2/3/5，跳过 GPIO4 因为它给了彩屏 DC）。

键值映射（keyboard.cpp 里的 keyMap）

物理键盘印的是 1-9/A-D/*/#，但代码里要把它们翻译成"功能键值"。这张映射表把物理位置对应到功能：

物理布局        →   功能键值
 1  2  3  A          KEY_1  KEY_2  KEY_3  KEY_UP(↑)
 4  5  6  B          KEY_4  KEY_5  KEY_6  KEY_DOWN(↓)
 7  8  9  C          KEY_7  KEY_8  KEY_FIRE  KEY_LEFT(←)
 *  0  #  D          KEY_BACK  KEY_ENTER  KEY_ENTER  KEY_RIGHT(→)

所以：A/B/C/D=方向，0或#=确认，*=返回，9=射击/硬降。这个映射表也是用键盘自检程序逐键验证过的。

五、底层驱动：把硬件变成函数

keyboard.cpp
4×4 矩阵键盘 · 行列扫描 · 人
原理（课程知识）：16 个键用 8 根线。4 行设为输出、4 列输入上拉；逐行拉低、读列，哪一列被拉低就是哪个键按下；配合延时二次确认消抖。
关键函数：scanKeyboard() 返回按下的键（带去重，按住只触发一次）；isKeyPressed() 检测是否按住（飞机连续移动用）。和 51 单片机用 P1/P2 口扫描键盘原理完全一样。
lcd_driver.cpp
ILI9341 彩屏 · SPI · 人机
原理：彩屏靠 SPI 高速传像素。逐像素发太慢，所以在内存里建一块 240×320 的帧缓冲（GFXcanvas16，约150KB），先把画面全画到内存，再整帧一次性推给屏幕。
关键函数：lcdFillRect / lcdDrawString / lcdDrawLine（画到内存）→ lcdRefresh()（推送到屏）。这块 150KB 帧缓冲也是为什么必须用 ESP32 而非 51的直接原因。
oled_driver.cpp
SSD1306 OLED · I²C · 746行 · 人机
原理：OLED 用 I²C 两根线驱动，自带中文字库（wqy GB2312），所以中文显示靠它。
内容：表情显示（眨眼、各种颜文字脸）、边框文字、以及后加的动态表情包播放（见第九节）。这是最大的驱动文件，因为表情和动画素材都在这。
audio.cpp
无源蜂鸣器 · PWM · 人
原理（呼应C51音乐）：无源蜂鸣器靠方波驱动，方波频率 = 音调高低。用 ESP32 的 LEDC 硬件 PWM 输出指定频率方波发声——这正是我们之前用 C51 定时器播放音乐思路的延续。
音符表：NOTE_C4=523, D4=587, E4=659... 一组标准音高频率。
非阻塞改造：把音效拆成"频率+时长"的序列，主循环每帧推进，发声不卡住游戏画面（原来用 delay 会顿）。

六、钢琴模块（piano_game.cpp，677行）—— 最用心的部分

钢琴是整个项目的起点和核心，也是我们花心思最多的模块。人主导

它在做什么

屏幕分 4 条竖直轨道，音符从上往下掉，落到底部判定线时按对应轨道键。按得准 → 判定 Perfect/Good，发出该音符的音调；按不准或漏掉 → Miss。不同轨道对应不同音阶，连起来就是一首曲子。还有长按音符、连击数(Combo)、命中率统计。

核心思路（三个关键设计）

① 音符"位置 ↔ 时间"的换算（判定的本质）

每个音符有一个出现时刻 tick。设计上让音符"在它的 tick 时刻正好落到判定线"，由此反推每一帧它应该在的 Y 坐标：y = 判定线 + (当前时间 - tick) × 每毫秒下落像素。这样"画面上音符到线"和"该得分的时刻"就严格对齐了。
★ 这正是我们 debug 出来的关键修复——最初版本判定时机和画面对不上，照判定线按反而 Miss，是在真机上发现并用这个公式修好的。

② 音高的动态映射（可玩性的关键）

最初设计是"4 个键固定 4 个音"，但 4 个音根本弹不成曲子。我们重构为：按对键就触发"当前乐曲此刻应当发出的音符"——按键只负责判定"中没中"，发什么音由乐曲的音高数组决定。这样一首《小星星》《欢乐颂》就能完整弹出来。

③ 音准校准（呼应 C51 音乐设计）

蜂鸣器用 PWM 方波发声、频率决定音高，这是我们之前用 C51 播放音乐的延续。但 ESP32 的实际听感音高需要校准——我们专门另开了一个测试工程，逐个试不同 PWM 频率的真实听感，校准了音符频率表，确保弹出来的调子是准的。

后期改进（真机体验驱动）

  • 人 音符到线自动发声：让旋律全程都能听到（按键负责评分），而不是只有按中才响。
  • 人 难度选择：进游戏先选简单/普通/困难，影响下落速度和判定宽松度。
  • 人 非阻塞重构：把 delay() 全换成基于 millis() 的计时，消除下落卡顿。

九、动态表情包（亮点技术）

让 128×64 的单色小屏显示会动的表情，是个有意思的技术点。人机协作

单色屏怎么显示图片

OLED 每个像素只有"亮/灭"，要显示图必须先转成单色点阵：每像素 1 bit，128×64 = 1024 字节，屏幕按这个 bit 数组逐点点亮。

我们的自动化流程

原始的手工做法是用 PCtoLCD 软件一张张转，18 张太慢。我们写了个 Python 脚本 tools_emoji_convert.py（基于 Pillow）批量处理：

原图(2048×2048彩色) → 降采样 → 缩放裁剪到128×64
  → 二值化(暗处点亮) → 打包成 XBM 字节数组
  → 生成 emoji_bitmaps.h(18个位图 + 5组动画表)

验证时还把图打印成 ASCII 字符画在终端预览，确认转换效果。

"动态"怎么实现

把同一个动作拆成 2~3 张分镜，按固定间隔循环切换 = 帧动画。18 张编成 5 组，在菜单待机和番茄专注时循环播放（每帧约 600ms、每组约 4.5 秒切换）。为省电只在帧变化时刷新——这条正是从欠压调试中学到的经验（降低刷新频率减小平均电流）。

技术串联这一个功能串起了：I²C 显示接口 + PROGMEM（把大位图放 Flash 而非 RAM）+ 供电优化经验。

  • 触发：主菜单输入 Konami 码 ↑↑↓↓←→←→ 9 0（菜单无任何提示），按对后蜂鸣器三声进入。
  • 功能：黑底绿字的十六进制内存编辑器 + 参数速改菜单，可实时调扫雷棋盘/雷数/透视开关等。
  • 安全设计：它操作的不是真实内存，而是一块专门的 64 字节沙盒 safeRAM，写操作带边界检查，越界/非法值一律拒绝，碰不到真实内存、不会崩溃。

技术上串联了"按键序列状态机"（识别 Konami 码）和"安全边界设计"（沙盒内存），是彩蛋也是一次小练习。
